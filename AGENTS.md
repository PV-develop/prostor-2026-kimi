# AGENTS.md

## Проект и источник кода

- Проект: сайт «Простор».
- Основной репозиторий: `PV-develop/prostor-2026` (`https://github.com/PV-develop/prostor-2026`). Основная ветка — `main`.
- GitHub — основной источник кода. Во время визуальных итераций работаем преимущественно с локальной копией репозитория.
- Не публикуем сайт, не создаём production-релиз и не отправляем изменения в GitHub без явного согласования с пользователем.
- Commit и push выполняем только после утверждения пользователем блока или логической группы правок, а не после каждой промежуточной итерации.

## Текущее состояние

Главная страница перенесена на Astro + TypeScript (статическая генерация). Экспорт
Claude Design сохранён как визуальный референс в `reference/claude-design/` и в корне
(`index.html`, `support.js`, `image-slot.js`, `fonts/`, `vendor/`); эти файлы не
участвуют в Astro-сборке и вручную не редактируются.

Актуальный код сайта:

- `src/pages/index.astro` — главная страница.
- `src/components/ui/`, `src/components/blocks/`, `src/components/layouts/` — библиотека
  компонентов (см. `docs/blocks.md`).
- `src/styles/design-tokens.css` — единый источник токенов дизайн-системы;
  `src/styles/global.css` — базовые стили и общие классы. См. `docs/design-system.md`.
- `src/content/home.ts` — контент главной (типизированные данные).
- `src/scripts/main.ts` — вся интерактивность на чистом TypeScript (меню, нить, частицы,
  reveal, счётчики, стрелки процесса, формы). Без React и других runtime-зависимостей.
- `public/` — локальные шрифты (`public/fonts`), логотипы и изображения
  (`public/images/{logo,cases,team,chips}`). Работающий сайт не должен зависеть от
  внешних CDN: никаких Google Fonts/Unpkg.
- `docs/` — `design-system.md`, `blocks.md`.

Команды (npm):

- `npm run dev` — dev-сервер;
- `npm run build` — production-сборка в `dist/`;
- `npm run preview` — просмотр сборки;
- `npx astro check` — проверка типов.

Запрещено: Tailwind и CSS-фреймворки, headless CMS, хардкод цветов/отступов/размеров
вне токенов, `href="#"`-заглушки (пункты на несозданные страницы скрываем с TODO,
разметку сохраняем), дублирование реализаций блоков между страницами.

Порядок проверки изменений: `npx astro check` и `npm run build` без ошибок, затем
просмотр страницы на 1440px и 375px (нет горизонтального скролла, нет 404 ресурсов,
консоль чиста), сверка с `reference/claude-design/`. Скриншоты итоговых состояний
сохраняем в `screenshots/astro/`.

Коммит и push выполняем только после утверждения пользователем; публикация —
только по отдельному явному указанию.

## Исходный этап (история)

Ниже — описание этапа статического экспорта, на котором версталась и утверждалась
главная. Оставлено для контекста.

Для локального просмотра текущего экспорта используем HTTP-сервер, а не открытие через `file://`, например: `python -m http.server 8000`, затем `http://localhost:8000/`. Перед запуском проверяем наличие выбранного инструмента. Не добавляем сборщик или зависимости только ради запуска статического экспорта.

## Порядок работы

1. Перед началом крупного этапа один раз проверяем состояние локального репозитория и синхронизируемся с GitHub. Не перезаписываем локальные правки; при расхождениях сначала разбираем их с пользователем.
2. Перед значительными изменениями убеждаемся, что используется актуальная версия репозитория. Изменения проходят через отдельную ветку, проверки и preview.
3. В начале этапа проверяем наличие всех нужных ресурсов локально. Не скачиваем повторно уже имеющиеся файлы и не обращаемся к GitHub для чтения файлов при каждой операции.
4. Дизайн и вёрстку развиваем в одной кодовой базе, без промежуточного экспорта. Визуальные итерации выполняем локально и не коммитим каждый промежуточный вариант.
5. Существующие блоки переиспользуем. Новые универсальные блоки добавляем в библиотеку, не копируя одну и ту же реализацию между страницами.
6. Каждую изменённую страницу проверяем на десктопе и мобильном. Проверяем не только внешний вид, но и затронутую интерактивность, ошибки консоли, горизонтальное переполнение и работу с локальными ресурсами.
7. После визуальных правок сохраняем preview-версию согласованным способом и передаём пользователю ссылку или расположение preview. Preview не считаем production-публикацией.
8. Перед завершением сообщаем, что изменено и как проверено. Если проверка или preview недоступны, прямо указываем это.
9. После утверждения логической группы правок отдельно согласовываем commit и push. Production публикуем только по отдельному явному указанию пользователя.

## Правки текущего экспорта

- Сохраняем существующую структуру секций `data-screen-label`, адаптивные маркеры `data-m` и действующие обработчики, если задача не требует их изменения.
- Не выполняем без необходимости глобальное форматирование `index.html`: это создаёт большой малополезный diff.
- Правки визуального референса не смешиваем с подготовкой или выполнением миграции на Astro.
- Не редактируем вручную сгенерированный `support.js`. Изменения страницы вносим в поддерживаемые проектные файлы.
- Новые изображения, шрифты и скрипты сохраняем локально. Работающий сайт не должен зависеть от внешних CDN.

## Целевая архитектура

До финализации и утверждения главной страницы миграцию на Astro не начинаем.

После утверждения главной:

- переносим её на Astro + TypeScript со статической генерацией;
- выделяем дизайн-токены, компоненты и библиотеку переиспользуемых блоков;
- сохраняем утверждённый внешний вид и поведение, проверяя десктопную и мобильную версии;
- кейсы и статьи храним в Markdown;
- типовые блочные страницы описываем через YAML;
- SEO-параметры храним вместе с соответствующей страницей, а редиректы — отдельно;
- интерактивность реализуем на JavaScript или React только там, где она действительно необходима;
- шрифты и скрипты подключаем локально, без зависимости работающего сайта от внешних CDN.

При миграции используем принятые в новой кодовой базе команды установки, проверки и сборки. Их нужно зафиксировать здесь после появления Astro-проекта. GitHub остаётся основным источником кода; путь изменений — ветка → проверки → preview → утверждение пользователя → production.
